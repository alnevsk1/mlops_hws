# План реализации и доказательств

Это план, не отчёт о выполненных экспериментах. Численных результатов пока нет.

## Связь с ДЗ 8–10

Продолжить FastAPI API из service.py: фабрика приложения, внедряемый backend,
проверка артефакта до готовности, фактически загруженная версия в ответах,
валидация запроса до генерации. Предыдущую рабочую копию не изменять.
Сохранить совместимый /generate и добавить потоковый интерфейс.
История передаётся клиентом; состояние диалога не хранится в Pod.

## Сервис

- Явный backend_mode=simulated; измерения называются TTFC/inter-chunk latency.
- Файлы имитатора A/B с SHA-256; проверка ожидаемого хеша перед прогревом.
- Ограниченные running/waiting, отказ 429 при полной очереди, тайм-аут ожидания.
  Освобождение слота при отмене и разрыве соединения.
- Ограниченный локальный LRU-кеш, явно заданные CPU-cost hit/miss.
  Вычисления вне event loop, чтобы probes отвечали под нагрузкой.
- Request ID, Pod и загруженная версия в журналах и потоковых событиях.
  Финальное событие отличает полный ответ от HTTP 200 с оборванным потоком.
- Раздельные startup/readiness/liveness, режим дефекта ранней готовности,
  отдельный режим никогда не готовой B.
- Graceful drain: исключение из трафика, ожидание распространения Endpoints,
  завершение активных потоков в пределах terminationGracePeriodSeconds.

## Стенд

Отдельный kind-кластер и namespace ДЗ 11. Две реплики API, ConfigMap,
CPU/RAM requests/limits. Два Service над одними Pod: обычный и ClientIP.
Helm values задают образ, версию, прогрев и replicas. Сервис читает монтируемый
params.yaml; runtime-настройки не дублируются в Python.
Образы закрепить версиями и сохранить фактически использованные digest.

Prometheus собирает каждый Pod через Kubernetes discovery. Grafana получает
provisioned datasource/dashboard. Добавить kube-state-metrics и resource metrics
API для HPA. Ограничить retention по времени и размеру и emptyDir тома.
Предварительный бюджет: до 6 GiB RAM и 15 GiB дополнительного диска;
уточнить до скачивания образов. Не очищать общие Docker-ресурсы.

## Матрица опытов

| Опыт | Сравнение | Доказательства |
|---|---|---|
| A1 | ранняя готовность / исправленные probes | запрос к холодному backend; Ready, EndpointSlice, журнал после исправления |
| A2 | A → B под нагрузкой | заранее начатый длинный поток; все попытки; ноль 5xx и обрывов в штатном rollout |
| A3 | неготовая B → rollback A | B не получает трафик; версия A подтверждена ответами |
| A4 | принудительная остановка | обрывы, обнаружение отказа, восстановление; retries отдельно |
| B | обычный/ClientIP × равномерный/80% от одного клиента | четыре клиентских Pod с разными IP; три повтора каждой комбинации, минимум 120 с измерения |
| B fix | исправление на том же расписании | очередь, TTFC, отказы, распределение по Pod |
| C | HPA 2 → 3 → 2 | CPU, HPA conditions, создание/Ready Pod, фактическое окно снижения |
| C hot | HPA с ClientIP | средняя CPU, работа новой реплики при горячем клиенте |
| Alerts | задержка / доля отказов | минимальный объём, for, pending → firing → normal |

Для B одинаково сбрасывать кеш перед каждым прогоном. Прогрев отделять от
120-секундной измерительной фазы. Для обычного Service использовать новые TCP
соединения, фиксировать keep-alive и source IP. Port-forward не подходит для
замера балансировки Service. Если перекос не возник, сохранить этот прогон.

## Генератор и метрики

Детерминированное расписание, seed=42. Сохранять запланированное и фактическое
время отправки, monotonic send/first/end, UTC для сопоставления с Prometheus,
client/attempt/request ID, Pod, версию, статус и число частей.
Отдельно считать запланированные, отправленные, завершённые, отклонённые,
оборванные и просроченные. Перцентили успехов сопровождать n и долями ошибок.

Histogram для TTFC и полной длительности; counters с ограниченным outcome;
gauges running/waiting. Request/session ID никогда не включать в labels.
Сопоставлять клиентские значения с histogram_quantile по сумме bucket с le
за одинаковые окна и одну популяцию ответов.

## Проверки и сдача

Минимум пять проверок: прогрев в Kubernetes; версия после rollback;
восстановление артефакта и диалога после замены Pod; учёт отказов и обрывов;
изоляция двух диалогов с контрольными строками.
Unit-тесты: unittest; HTTP-клиент: HTTPX.
Для исправленного дефекта сохранить исходный сбой и повтор после изменения.

Четыре графика: rollout/Ready; TTFC/очередь по Pod; политики по трём повторам;
HPA/нагрузка по времени. report.html содержит реальные данные, ограничения
и ревью решения «очередь 3 с против пересчёта 0,8 с».
Кейс компании выбрать после получения лекции 11 и проверки первичного источника:
рядом с условием файл лекции пока отсутствует.
